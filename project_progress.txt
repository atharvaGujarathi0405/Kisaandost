3. WSL2 ASR ENVIRONMENT (NeMo requires Linux; Windows pip install unsupported)
------------------------------------------------
- Separate venv: .venv-asr-wsl (WSL2 Ubuntu, Python 3.12.3), fully isolated
  from the downloader's Windows .venv.
- AI4Bharat NeMo fork installed (nemo-v2 branch, "asr" extras only, not the
  heavier "all" extras).
- torch 2.14.0+cpu (CPU-only build deliberately chosen; no NVIDIA GPU on this
  machine, avoided pulling multi-GB CUDA/cuDNN packages).

Dependency incompatibilities found and fixed (all pins applied via pip in the
WSL venv; NOT hand-edited into NeMo's own source):
  - pytorch-lightning pinned to ==2.2.1 (NeMo's own declared floor). Newer
    releases removed NeptuneLogger, which exp_manager.py imports unconditionally.
  - datasets upgraded to >=2.20,<3 (was auto-resolved to 2.14.4, which used a
    pyarrow API removed in the very new pyarrow that also got installed).
  - numpy.sctypes compatibility shim added in asr_baseline/model.py
    (_shim_numpy_sctypes) - NeMo's audio loader reads this NumPy 1.x-only
    attribute; restoring just the two keys it needs avoided downgrading numpy
    globally (which would fight pandas/scipy's numpy>=2 requirement).

Model-loading fix (in asr_baseline/model.py only):
  - ASRModel.from_pretrained(MODEL_NAME) is BROKEN for this specific repo: it
    guesses the checkpoint filename as "{model_name}.nemo", but the actual
    file in the repo is "indicconformer_stt_mr_hybrid_rnnt_large.nemo" (no
    "_ctc"). This mismatch sends it down a broken "download whole repo as an
    already-extracted directory" fallback path.
  - Fix: hf_hub_download(repo_id=MODEL_NAME, filename=CHECKPOINT_FILENAME)
    followed by ASRModel.restore_from(restore_path=..., map_location=device).
    This is what from_pretrained()'s own docstring recommends for a local
    .nemo file.

transcribe_one() fix (asr_baseline/model.py):
  - In "ctc" decoder mode this model's transcribe() returns a nested list
    (e.g. [[' text']]) instead of a flat list of Hypothesis objects. Added a
    while-unwrap loop. No effect on the actual transcribed words.

Access: the HF repo is gated. User created a HuggingFace token, accepted the
model's terms, token stored in .env (gitignored) as HF_TOKEN, read via
os.environ in model.py. The model is now cached, so runs use HF_HUB_OFFLINE=1.

Other environment issues hit and resolved:
  - WSL DNS was completely broken at the start (systemd-resolved stub had no
    upstream servers). Fixed by user running (with sudo, outside this
    session): echo "nameserver 8.8.8.8" > /etc/resolv.conf
    It has since reverted; see section 11.
  - WSL's exec layer hung once (HCS_E_CONNECTION_TIMEOUT) after a background
    job was interrupted mid-session; resolved itself after the machine was
    left overnight / WSL cold-started fresh.
  - pytest was missing from the WSL venv and could not be installed (DNS), so
    the test suite currently runs on Windows only.

6. P0 - CHUNKED INFERENCE (commit 6f81bcd)
------------------------------------------------
Chose chunking over raising the WSL memory cap: it works on any machine and
keeps memory flat. asr_baseline/chunking.py; model.py and all earlier fixes
untouched.
  - Audio longer than max_chunk_sec is split at the quietest 25 ms frame
    between target and max seconds (defaults 20 s / 30 s, overlap 0).
    Configurable via --chunk-sec / --max-chunk-sec / --overlap-sec or the
    ASR_CHUNK_SEC / ASR_CHUNK_MAX_SEC / ASR_CHUNK_OVERLAP_SEC env vars.
  - Per-chunk resume + failure recovery in asr_outputs/chunks/<stem>.csv:
    finished chunks are skipped, failed ones retried. --force clears both levels.
  - Stitching: overlap 0 -> disjoint chunks joined in order. Overlap > 0 ->
    longest common run of >= 2 words (difflib) at each seam. Exact
    suffix/prefix matching was tried first and FAILED on a real seam (edge
    words heard differently: "बनच्या" vs "ह वन्याच्या"), so it was replaced.
  - Output stays raw. Logs: logs/asr_baseline.log. Docs: docs/asr_baseline.md.

Measured: JHN_001 (473.6 s) -> 19 chunks, 53.9 s inference, peak RSS 1.74 GB
(the single pass had been OOM-killed at ~6 GB). QUALITATIVE: on the 30 s
sample, chunked output was nearly identical to single pass (a few boundary
spellings differ).

9. P1b - VAHNT TEXT FORCED ALIGNMENT (option b)
------------------------------------------------
varhadi_data/vahnt_text.py, varhadi_data/align.py, scripts/vahnt_align.py.
  - Text fetched with Playwright, like the downloader (bible.com blocks plain
    HTTP with a JS challenge). Keeps section headings + verse text; drops
    verse numbers, cross-references and footnotes. Stored verbatim with URL
    and fetch date.
  - All 89 chapters fetched. 39 have bridged verses (e.g. LUK.2.22+23+24);
    checked: no verse text missing in any chapter.
  - Alignment: numpy CTC Viterbi (no new dependency; torchaudio not installed)
    on the baseline model's Marathi CTC log-probs, computed per silence-cut
    chunk. Audio before the first word and after the last may stay unaligned,
    which absorbs the spoken book/chapter announcement. Segments are ~20 s or
    shorter, cut between verses.
  - Pilot JHN_001: 31 segments covering 6.32-471.56 s. For all 31, the
    baseline's own decode starts/ends on the same words as the aligned text
    (automatic check, NOT a listening test).
  - QUALITATIVE OBSERVATION: text vs baseline differences are mostly
    systematic Varhadi -> standard Marathi forms: काई->काही, नाई->नाही,
    त्याले->त्याला, पयले->पहिले, देला->दिला, म्हतलं->म्हटलं. This is exactly the
    gap adaptation targets. CER vs the published text (median 0.125) is NOT a
    verified baseline metric.
  - Bias rule: never filter the evaluation set on alignment score or on CER
    vs the baseline; that would keep only what the baseline already gets right.
  - gold-import-alignments queues aligned segments as pending_review, with the
    published text as candidate reference (never auto-verified).
  - Full run (align --all): 40/89 chapters aligned (0 failures, peak RSS
    2.1 GB). Claude Code's background-job manager stopped it twice for low
    system memory (not a code failure). A rerun skips finished chapters.
  - Review queue: 1,296 candidate segments, 5.54 h, 40 chapters, all
    pending_review. 54 score below -1.5; their boundaries still match, the
    mismatch is inside (e.g. translator notes in parentheses in the published
    text that the narrator likely does not read).
  Bugs found + fixed: a verse continuing in a new paragraph was glued onto the
  previous word; int8 overflow in the alignment backtrace on real-length input
  (NumPy 2); the "page loaded" wait only matched chapter 1 and then missed
  chapters that start with a bridged verse (LUK 22, MAT 15, MAT 17).

9c. P1d - CONFIDENCE-BASED TRIAGE (prompt03.md, 2026-10-04)
------------------------------------------------
Goal: cut manual review effort WITHOUT treating automatic text as ground truth.
- varhadi_data/triage.py + varhadi_data/triage_config.json (version triage-v1;
  every weight and threshold lives in the config). scripts/triage_gold_candidates.py
  (--chapter / --all / --threshold / --review-threshold / --export-csv / --report)
  writes ONLY the triage columns of the gold CSV, plus
  data/evaluation/triage_report.csv and triage_summary.json.
- Formula: confidence = 0.35*alignment + 0.30*ASR agreement (CER + ins/del rate)
  + 0.15*audio quality (silence, clipping, loudness) + 0.10*duration
  + 0.10*speaking rate - artifact penalties (parentheses 0.25, empty ASR 0.30,
  digits/Latin 0.15, repeated word 0.15, heading 0.05), clipped to [0,1].
  ASR decoding stability: NOT AVAILABLE (would need re-decoding).
- Status: HIGH_CONFIDENCE_CANDIDATE >= 0.90 (final score, no blocking flag);
  REJECT_CANDIDATE if base score (before penalties) < 0.50 or a hard failure;
  otherwise NEEDS_REVIEW. Thresholds set from the real distribution
  (0.90 ~= median) and PROVISIONAL until compared with human decisions.
- Calibration finding: the first version auto-rejected 9 segments whose only
  problem was an unread translator note in parentheses (good audio). Policy
  changed: correctable text artifacts block HIGH_CONFIDENCE but never cause
  rejection.
- Results, all 1,296 candidates: HIGH_CONFIDENCE 718 (UNVERIFIED), NEEDS_REVIEW
  573, REJECT 5. Confidence median 0.909. Flags: contains_heading 222,
  parentheses 22, speaking_rate_out_of_range 4, duration_out_of_range 1.
- JHN_001 pilot (31): NEEDS_REVIEW 11, HIGH_CONFIDENCE 20, REJECT 0. JHN_001 is
  the TEST chapter, so all 31 still need human review; triage only orders them.
- Known bias: the agreement signal uses the baseline model (circular), so triage
  may order review but must never select test data.
- review_server.py upgraded: queue NEEDS_REVIEW -> REJECT -> HIGH, lowest
  confidence first; shows candidate, baseline ASR, scores, flags, duration,
  progress (reviewed/verified/corrected/rejected/remaining + triage counts);
  keys V/E/R/A/Space/N/P; auto-advance; notes field; state lives only in the CSV
  (safe across refreshes and crashes). Reviewer IDs validated (2-20 chars, no
  names or phone numbers).
- gold.py: new triage + review_notes columns (existing columns unchanged);
  VERIFIED/CORRECTED/REJECTED accepted as aliases of correct/needs_correction/
  rejected.
- build_manifests.py: gold-only by default. --include-unverified writes pending
  HIGH_CONFIDENCE segments as PSEUDO_LABELED to SEPARATE files
  (train/val_pseudo_labeled_manifest.json); the test split is always gold-only.
- Integrity checks: 0 non-triage fields changed; downloader files unchanged vs
  git; 0 of 89 MP3s modified; 0 gold labels created. Docs: docs/gold_review.md.
